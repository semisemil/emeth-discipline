# 스킬 프롬프트 작성 원칙

이 원칙은 `skills/` 아래의 스킬 본문, reference, 예시와 호출 메타데이터를 만들거나 수정할 때 적용한다. 목표는 문장 수를 줄이는 것이 아니라, 필요한 행동 변화는 유지하면서 불필요한 컨텍스트 비용과 반복 추론을 없애는 것이다.

## 성능·비용 계약

Emeth Discipline 최적화의 목표는 최저 토큰 사용량이 아니라 **무스킬 대비 품질 우위를 최소한의 추가비용으로 얻는 것**이다. 품질은 제약조건이고 비용은 그 제약을 통과한 후보 사이의 최적화 대상이다.

- 복잡하거나 실패 위험이 큰 대상 작업에서는 무스킬 실행보다 성공률이나 결과 품질이 실질적으로 높아야 한다.
- 스킬이 품질을 더 높일 여지가 작은 단순 작업에서는 무스킬과 동등한 품질을 유지하고 추가비용을 작게 제한한다.
- 기존 스킬보다 비용이 낮아도 성공률, 요구 충족, 범위 보존, 검증 신뢰도가 나빠진 후보는 채택하지 않는다.
- 스킬 자체의 Gate 통과나 자기 보고만 품질 근거로 사용하지 않는다. 고정된 외부 검증기, 결과물 검사 또는 블라인드 평가로 실제 결과를 판정한다.
- 캐시 입력, 비캐시 입력, 캐시 쓰기, 출력과 실제 API 등가 비용을 분리하고, 최상위 작업과 모든 하위 작업의 사용량을 합산한다.

## 원칙

1. **모델이 이미 안정적으로 수행하는 내용은 쓰지 않는다.** 일반적인 모델 역량, Codex 기본 지침, 저장소 지침과 겹치는 설명은 제거한다. 스킬에는 해당 도메인에서 새로 필요한 지식, 선택 기준, 반복해서 관찰된 실패의 교정만 둔다.
   - 하위 작업 전달문에는 해당 작업이 이미 상속받는 시스템·개발자·프로젝트·`AGENTS.md` 지침을 복사하거나 요약하지 않는다. 전달문은 역할별 고정 계약과 이번 배정에서 새로 생긴 값만 담는다.
2. **같은 의미는 한 곳에만 둔다.** 하나의 요구사항에는 하나의 권위 있는 위치를 정하고, 다른 위치에서는 참조한다. 해당 위치의 이해에 꼭 필요한 경우에만 반복한다. 소절마다 하나의 일관된 주제를 다루고, 제목이나 형식을 채우기 위해 같은 내용을 반복하지 않는다. 조건부 세부사항은 reference로 옮기고 본문에는 언제 읽는지만 남긴다.
3. **행동을 바꾸지 않는 문장은 통째로 삭제한다.** 문장을 짧게 고쳐 남기기보다, 그 문장이 없을 때 결과·판단·도구 사용·허용 범위가 달라지는지 확인한다. 달라지지 않으면 문장 전체를 제거한다. 표현 방식과 절차의 세부 조건은 필요한 결과나 실제 실패와 연결될 때만 둔다. “굵게와 기울임을 활용한다”로 충분하면 용도별 조건을 추가하지 않는다.
4. **원하는 행동과 결과를 긍정형으로 쓴다.** 금지 사항을 길게 나열하기보다 모델이 선택해야 할 행동, 유지해야 할 정보와 도달해야 할 상태를 직접 쓴다. 반복해서 발생한 고위험 실패처럼 금지 자체가 필요한 경우에만 부정형을 둔다.
5. **모든 작업에 필요한 내용만 본문에 둔다.** 스킬이 호출될 때마다 필요한 핵심 절차와 판단 기준만 `SKILL.md`에 둔다. 특정 작업 유형에만 필요한 UI, 코드, 도구, 형식과 상세 예시는 필요한 때만 읽는 reference나 실행 가능한 script로 분리한다. 도구 안내에는 올바른 호출에 필요한 입력과 결과 해석을 남긴다. 자동 처리되는 내부 동작은 호출자의 판단에 필요할 때만 설명한다.
6. **과정보다 관찰 가능한 결과를 서술한다.** “다시 읽어라”, “검사하라”, “충분히 검토하라”처럼 범위가 없는 내부 과정을 요구하지 않는다. 대신 최종 산출물이 만족해야 할 상태, 판단에 반영할 근거, 허용된 변경 범위와 실패 조건을 쓴다. 특정 순서나 도구가 결과의 정확성에 필수일 때만 과정을 지시한다.
7. **문장이 유발하는 컨텍스트 비용까지 센다.** 프롬프트 자체의 토큰 수뿐 아니라 각 문장이 새로 읽게 만드는 파일·대화 이력·검사 범위를 비용에 포함한다. 이 비용에 Slice 수와 재시도 가능 횟수를 곱해 정상 경로와 조건부 실패 경로를 따로 평가한다. 변경되지 않은 근거는 재사용하고, 실패할 때만 필요한 세부 절차는 조건부 reference로 분리한다. 불필요한 탐색을 유발하는 문구는 금지문을 덧붙이기보다 그 유발 문구부터 제거한다.
8. **유효한 근거를 재사용하고 필요한 정보를 보완한다.** 읽기·검색·검증·검토 결과는 관련 코드와 조건에서 여전히 같은 판단을 뒷받침하면 재사용한다. 추가 조회는 판단에 필요한 정보에 맞춰 범위와 출력량을 선택한다. 명시된 필수 검증을 유지하고, 변경 위험과 새로 얻은 정보에 맞춰 검증 범위를 조정한다. 검증 방법은 요구 결과를 판별할 수 있는 것으로 선택하며, 확인할 수 없는 결과는 미확인으로 남긴다.
9. **각 스킬은 자신의 책임만 기술한다.** 스킬에는 자신의 산출물과 완료 조건을 둔다. 호출자의 후속 실행과 작업 조율은 호출자가 책임진다.
10. **결정론적 처리는 코드에 맡긴다.** ID 발급, 메타데이터 생성, 리비전 증가처럼 규칙으로 결정되는 값은 명령이 처리한다. 모델에는 의미를 판단해야 하는 입력만 맡긴다.

## 수정 절차

1. 교정하려는 실제 실패와 기대하는 관찰 가능 결과를 먼저 적는다.
2. 각 문장이 모델 기본 역량이나 상위 지침과 겹치는지 확인한다.
3. 같은 의미를 가진 문장을 하나의 권위 있는 위치로 합친다.
4. 내부 과정을 요구하는 문장을 기대 결과와 판단 기준으로 바꾼다.
5. 제거해도 행동이 달라지지 않는 문장을 삭제한다.
6. 수정 전후의 실제 토큰 수, 문장이 추가로 불러오는 컨텍스트 범위, Slice·재시도 반복 배수와 대표 사례의 행동을 각각 확인한다. 정상 경로와 조건부 실패 경로를 구분하며 문장이나 단락 수 감소만 압축 근거로 사용하지 않는다.

## 유지 여부 판정

문장을 남기려면 다음 중 하나를 구체적으로 답할 수 있어야 한다.

- 어떤 기대 행동이나 결과를 만든다.
- 어떤 관찰된 실패를 막는다.
- 어떤 도메인 지식, 계약 또는 도구 사용법을 제공한다.
- 어떤 선택의 자유도를 의도적으로 제한한다.

어느 항목에도 해당하지 않으면 삭제한다.
