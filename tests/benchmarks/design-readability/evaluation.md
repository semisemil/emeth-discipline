# 설계문서 읽기 평가

설계 스킬의 변경 전후 결과물을, 독자가 설계를 이해하고 판단하는 데 드는 노력으로 비교한다.
분량, 제목 수, 다이어그램 수는 품질 점수로 사용하지 않는다.

## 실행 과제

| 과제 | 최초 요청 | 확인할 경로 |
| --- | --- | --- |
| Graph Panel | `첨부한 HANDOFF.md를 가지고 $emeth-discipline:architecture-coop 해주세요.` | 탐색 후보, 통합된 아키텍처, 독립 검토 |
| CLI quiet 옵션 | `아래 요청을 $emeth-discipline:development-design으로 설계해 주세요.` 뒤에 small-cli.md 원문을 전달한다. | 후보 비교가 필요하지 않은 설계, 문서 작성, 독립 검토 |

Graph Panel 과제의 HANDOFF.md에는 [graph-panel.md](graph-panel.md) 원문을 그대로 사용한다.
이 입력에는 과거에 성공했다는 CDP 검증 코드나 실제 화면이 포함되지 않았다.
그 자료를 추가한 실행은 추가 자료가 없는 실행과 구분한다.
과거 연결 성공이라는 사용자 진술과 패널 삽입의 실현 가능성은 별개의 사실이다.

각 버전의 플러그인을 별도로 설치하고, 같은 원문과 초기 작업 공간으로 새 Codex 작업을 시작한다.
모델, 추론 수준, 상위 지침, 권한, 도구와 하위 역할 설정을 유지한다.
생성 작업에는 이 평가 문서, 예상 결함, 개선 제안이나 다른 실행 결과를 전달하지 않는다.
스킬이 요구하는 후보와 검토 절차를 수행하며, 사용자가 결정해야 하는 내용은 미결정으로 남긴다.
최종 응답, 연결된 설계문서, 후보와 검토 보고서, 실행 원문과 설정을 각각 보존한다.

## 독립적인 읽기 평가

생성에 참여하지 않은 평가자에게 버전을 가린 결과물과 원래 요구사항을 제공한다.
평가자는 먼저 최종 문서를 읽고, 다음 질문의 답과 근거 위치를 기록한다.
후보나 검토 보고서까지 찾아야 답할 수 있다면 그 이동과 재조립이 왜 필요한지 기록한다.

| 독자의 질문 | Graph Panel에서 확인할 내용 |
| --- | --- |
| 무엇을 만들며 기존 시스템 어디에 연결하는가? | 앱 내부 패널, 기존 Proofline 영역 보존, UI Adapter와 Renderer의 연결 |
| 누가 무엇을 소유하며 데이터는 어떻게 흐르는가? | 그래프 원본, 전달과 검증, 렌더링, 사용자 화면 상태의 소유와 관계 |
| 대표 동작과 실패를 따라갈 수 있는가? | 초기 부착, JSON 갱신, 스레드 전환, 해제, 삽입 실패 시 기본 화면 보존 |
| 무엇이 정해졌으며 무엇이 남았는가? | 선택한 설계, 사용자 승인이나 근거가 필요한 선택, 영향을 받는 부분 |
| 그림과 본문으로 같은 설계를 이해할 수 있는가? | 구성 요소, 방향, 경계와 상태의 일치, 그림이 설명하는 구체적인 관계 |

CLI 과제에서는 quiet 옵션의 범위, stdout과 stderr의 역할, 종료코드와 실패 동작을 같은 방식으로 확인한다.
독자가 이 정보를 찾고 연결하는 데 필요한 설명은 유지되어야 한다.
결정의 근거와 관계를 생략한 짧은 문서나, 같은 내용을 반복하는 긴 문서는 모두 읽기를 방해할 수 있다.

각 답은 `바로 이해`, `추적 필요`, `판단 불가`로 구분하고, 실제 위치와 이해를 막는 원인을 적는다.
시각화는 관계나 흐름의 이해에 기여하는지 평가하며, 형식이나 개수만으로 가산하지 않는다.
전체 판정은 `더 읽기 쉬움`, `동등`, `더 읽기 어려움`, `비교 불가` 중 하나로 제시한다.
구조와 계약의 정확성은 읽기 평가의 전제이며, 틀린 설계를 쉽게 읽을 수 있다는 이유로 개선으로 판정하지 않는다.

## 검토 절차의 결함 탐지

[review-cases.md](review-cases.md)의 각 결과물을 원래 CLI 요청과 함께 기존 독립 설계 검토에 전달한다.
아래 예상 결과는 검토자에게 전달하지 않는다.
각 사례는 문서 길이와 무관하게 독자의 이해나 설계 판단을 방해하는 내용을 검사한다.

| 사례 | 원래 요청에서 도출한 판정 근거 |
| --- | --- |
| A | 제목은 있지만 옵션 판정, 출력 책임과 호출 관계가 연결되지 않아 동작을 복원해야 한다. |
| B | 이름만 나열되어 quiet 판정과 출력 채널을 누가 소유하는지 알 수 없다. |
| C | 후보 비교만 있어 최종 설계를 판별할 수 없다. |
| D | 계약, 수정 요청과 검토 결과가 섞여 현재 적용할 동작을 판별할 수 없다. |
| E | quiet의 적용 채널이 결정되었다면서 같은 내용을 미결정으로 남겨 구현 상태가 모순된다. |
| F | 실패 시 stderr 계약과 시각화의 출력 경로가 요청 및 본문과 모순된다. |
| G | 정상 대조 사례다. 더 많은 절이나 새로운 구성 요소를 요구하는 지적은 결함 탐지가 아니다. |

검토가 제목이나 키워드만으로 통과시키거나, 정상 사례에 내용을 늘리는 것만 요구하면 실패로 기록한다.

## 결과 보고

원문과 설치본의 해시, 실제 실행 경로, 모델과 하위 역할, 완료 여부와 산출물 경로를 남긴다.
변경 전후의 독자 질문별 결과, 의미가 달라진 계약, 미확인 사항을 비교한다.
사용량이나 비용을 비교할 때는 하위 작업까지 수집하고, 누락과 실행 조건 차이를 명시한다.
한 번의 결과만으로 일반적인 품질 향상이나 비용 효과를 확정하지 않는다.
